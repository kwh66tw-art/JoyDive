## 二、架構層決策回顧

### 2.1 F5/F6：從「本地 fork」到「家族共用套件」

**決策內容**：`JD2Core/Algorithm/` 的本地 Bühlmann/DiveEngine fork（含 Ultra
側稽核已知的 9 項安全級問題）整包刪除，改用 SPM local path 引用家族統一
`DiveKit`；15 種格式解析器同理搬遷至 `DiveImportKit`，本地只留一個
Adapter 檔案作為唯一進入點。

**為什麼是對的**：
- 本地 fork 是「休眠死碼」——零呼叫端引用，卻帶著已知安全問題，一旦被 UI
  接上就會從休眠變成活的風險程式碼。刪除比修復更乾淨。
- Adapter pattern（`DiveImportKitAdapter.swift`）把「家族共用邏輯」與
  「App 本地錯誤處理/UI 串接」切開，符合「單一戰場」原則——之後 Kit 有
  bug，回 Kit 修一次，三個 App 都受益，不會各自修各自的。

**這次踩到的架構陷阱（值得記錄，供其他 App 參考）**：
- **Adapter 複製同名 error enum 的維護陷阱**：`DiveLogImporter.swift` 的
  本地 `DiveLogImportError` 刻意複製 Kit 的 errorDescription 樣板文字（為
  了給 App 層 catch-by-case），但這造成「Kit 端改了樣板文字，本地複製版
  沒跟著改」的漂移——2026-07-25 Kit 把中文樣板改英文，本地複製版沒有連帶
  修，使用者看到的仍是舊中文，表面上像「Kit 修復沒生效」，實際上是兩份
  重複定義各自為政。已記錄在 `SYNC_TO_JD2-ULTRA.md` #8，提醒 Ultra 未來
  採用同款 adapter 模式時注意。
- 教訓：「App 本地複製 Kit 的資料結構以取得型別安全」這個模式本身沒有機制
  防止兩邊漂移，是架構設計就存在的陷阱，不是一次性 bug；比較根本的解法是
  「只轉換 case 結構，直接沿用 Kit 的字串」而非複製樣板文字本身。

### 2.2 SwiftData Schema 的演進策略

v1.0→v1.2 多次 additive 欄位新增（`avgDepth`／`importExtrasJSON`／
`sourceFormat` 等），全程堅持「新欄位一定要有預設值，讓 lightweight
migration 自動處理」，沒有一次需要寫 `SchemaMigrationPlan`。這個紀律在
schema 變動頻繁的階段（見 `DiveLog.swift` 實際欄位數已遠超 ARCHITECTURE.md
原始文件記載）證明是正確的選擇——用小心的欄位設計換取零 migration 程式碼
的複雜度。

## 四、工作方法復盤

### 4.1 三層驗證的價值差異（這輪最大的方法論收穫）

這輪 WCAG 稽核經歷了「程式碼複查 → 模擬器實測 → 真機測試」三層，每一層
都抓到前一層看不到的真違規：

1. **程式碼複查**：抓到「Dynamic Type 沒有硬編碼字級」——但這個結論是
   不完整的，因為它看不到「3 欄橫排卡片在極限字級下整體重疊」這種**組合**
   效應。
2. **模擬器實測**（`xcrun simctl ui content_size` + 截圖）：抓到上述重疊
   問題，也抓到 Dark Mode 對比不足的具體元件（用 Python/PIL 算真實像素
   對比值，不是目測）。
3. **真機 VoiceOver 走查**：抓到 4 個前兩層完全看不到的問題（`DetailRow`
   朗讀英文、`DatePicker` 朗讀英文、Save 鍵停用無提示、翻譯誤植）——這些
   全部是「畫面顯示正確，但只用耳朵聽才會發現」的病灶類別，純視覺/程式碼
   審查在結構上做不到。

**教訓**：「只審程式碼就打勾」是不夠的判斷依據，這在本次會話裡至少被
明確記錄下來提醒過一次（附錄 2 開頭原話）。能跑模擬器就該跑，能上真機
就該上真機，三層各自的驗證盲區不重疊，不能互相取代。

### 4.2 第三方 AI 稽核報告的雙面性

這輪處理了兩份第三方 AI 稽核報告。**價值**：第一輪抓到 4 項真實存在的
風險（Buhlmann chunking bug、匯入去重漏洞等），修復後成為正式回歸測試。
**陷阱**：第二輪報告本身包含多項幻覺內容（宣稱「只支援 6 種語言」，實際
18 種；多處程式碼片段直接編造、檔案裡查無此行；指控的不一致其實不存在）。

**教訓**：外部/AI 生成的稽核報告要逐項自己 grep/查證再採信，不能因為
「聽起來專業、格式完整」就照單全收；報告的自信程度與其準確度無關。

### 4.3 送審駁回的「已完成」記錄陷阱（本次最關鍵的一次教訓）

2026-07-25 記錄「App Privacy 問卷已改為 No」，但 2026-07-28 送審前重新
逐格核對 ASC 現況，發現三格資料的「Third-Party Advertising」用途勾選
其實還在——07-25 的操作很可能是改到了另一個相鄰但獨立的問卷欄位。

**教訓（已寫入專項報告，這裡摘要方法論層面的部分）**：
- 「已在後台完成」的記錄如果只寫結論、不寫具體操作路徑（哪個畫面、哪個
  控制項），就無法回溯驗證，等於一筆無法查證真偽的記錄。
- 送審前的「已完成」清單，最終驗證基準應該是**重新整理後即時讀取的畫面
  狀態**，不是操作當下的記憶或幾天前的截圖——這次能抓到問題，關鍵就是
  沒有直接相信文字記錄，而是重新在 ASC 上逐格打開問卷核對。
- Apple 後台介面本身的問卷結構會改版，舊的心智模型（例如「有一個獨立的
  used-to-track 開關」）可能已經不對應現在的畫面，操作前若發現眼前畫面
  跟記憶不符，應假設自己記錯或介面改了，重新完整走一次，不要憑印象跳著
  確認。

### 4.4 文件正確性的「全盤」意味著系統性 grep，不是逐份翻閱

本輪文件校對過程中，同一個過時敘述（語言切換機制的舊做法）在
`ARCHITECTURE.md`／`UI_UX_SPEC.md`／`docs/LOCALIZATION_GUIDE.md` 三處
重複出現，但一開始是逐份翻閱到才發現、不是一次抓齊。改用「先列出已知會
被多份文件重複描述的事實類別，針對每一類 grep 全專案 `.md`」的方法後，
才真正系統性地抓出全部殘留（含 §8.3 效能目標表、DiveLogDetailView 現況
等零散殘留）。**教訓**：「全盤更新」的操作單位應該是「事實」，不是
「文件」——同一個事實在 N 份文件裡重複出現時，要一次改齊 N 處，不是改完
一份文件就標記完成、指望下一份文件不會有同樣的錯。

## 五、設計面回顧

- **18 語言 + App 內建切換器**：範圍從 v1.0 規劃的 3 語言擴大到 18
  語言，是本專案最大的範圍變更之一。多輪真機測試抓到的問題類別很集中：
  單一語言的曆法差異（泰文佛曆年）、格式化字串長度差異（越南文最長，
  導致版面截斷）、`String(localized:)` 與 `Text(LocalizedStringKey)`
  對 environment locale 的反應不一致——這些都是「多語言支援」在表面之下
  的真實複雜度，不是翻譯內容本身的問題。
- **無障礙優先（Accessibility First）**：不是口號，這次真的因為真機
  VoiceOver 走查抓到多個「視覺正確、但語音體驗錯誤」的問題，且這類問題
  結構上無法被程式碼審查或模擬器測試取代。
- **地圖無障礙的已知限制**：VoiceOver 下無法縮放/平移/展開聚合，判斷為
  MapKit 手勢與 VoiceOver 手勢接管的固有限制，不是這次能小修解決的問題，
  已如實記錄為已知限制並排入下一版 backlog，而非為了趕上架臨時湊一個
  沒驗證過的方案——這個「不趕工湊方案」的判斷本身也是一種設計紀律。

## 六、總檢討

### 做對的事

1. F5/F6 架構遷移的時機與執行方式——趁本地 fork 還是死碼、還沒被 UI
   接上之前完成遷移，避免了「先讓風險程式碼上線、之後再遷移」的更危險
   順序。
2. 三層驗證方法論（程式碼/模擬器/真機）在無障礙稽核上被完整走過一次，
   且每層都有記錄下抓到什麼、漏掉什麼，形成可複製的流程。
3. 對外部稽核報告（無論人類或 AI 生成）保持「逐項查證再採信」的態度，
   沒有因為報告格式完整就照單全收，也沒有因為第一份報告部分失準就全盤
   不信任第二份。
4. 發現「記錄與實況不符」時選擇重新驗證而非信任記錄——這直接避免了帶著
   一個實際上沒修好的隱私聲明錯誤送審。

### 可以改進的地方

1. **「已在後台完成」類型的操作記錄，應該在記錄當下就包含可回溯的具體
   路徑或截圖**，而不是等到下一次送審前才發現記錄不可信、需要重新驗證
   一遍。這是流程紀律問題，不是能力問題。
2. **文件同步應該用「事實驅動」而非「文件驅動」的方法從一開始就執行**：
   本次是在使用者追問「其他文件也查了嗎」之後才轉向系統性 grep 的做法，
   如果一開始就用這個方法，可以少走一輪逐份翻閱才發現遺漏的過程。
3. **Adapter 複製 Kit 資料結構的模式**（§2.1 提到的維護陷阱）目前只在
   一處加了文字提醒，沒有機制性的防呆（例如自動化測試比對本地 enum 與
   Kit enum 的字串內容是否一致）。如果 Ultra 未來採用同款模式，建議一併
   評估要不要加這類防呆測試，而不是只靠人工記得同步。
